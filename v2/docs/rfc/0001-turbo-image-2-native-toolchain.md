# RFC 0001: TurboImage 2.0 native toolchain and architecture

- Status: Accepted and implemented. This is the detailed record of how 2.0 behaves.
- Date: 2026-11-16, kept up to date as the implementation changed
- Supersedes: the 1.x layout at the repository root (`ios/`, `android/`, `src/`)

Reading order: [`../architecture.md`](../architecture.md) is the overview
(the parts, the rules, the contracts), and [`../adr/`](../adr/README.md) has
one record per decision with its reasons. This document is the detail behind
both. Its section numbers are stable, because the source comments cite them
("RFC §4.2a"); new material gets a new lettered subsection, not a renumbering.

## 1. Summary

TurboImage 2.0 is a New Architecture-only rewrite. It has four parts:

- a **C++20 core** that owns request semantics and is shared by iOS and Android,
- a **Fabric component** generated by Codegen,
- **replaceable loader adapters**: Nuke 14.0.0 on iOS and Coil 3.6.3 on Android,
- a **Bun-workspace monorepo** under `v2/` that builds with SwiftPM (or CocoaPods), Gradle and CMake.

This RFC fixes the toolchain baseline and the module boundaries. Pipeline work
was held back until the minimal example built on both platforms. That gate has
been met (§9), and the port of the 1.x pipeline that followed is recorded in
§4.2a and §4.4–§4.5c.

## 2. Goals and non-goals

Goals:

1. Identical request semantics on both platforms: cache keys, cache tiers and validation.
2. Nuke and Coil can be swapped without touching JS or Fabric code.
3. SwiftPM is the preferred iOS integration, and CocoaPods behaves the same during the migration.
4. Every production dependency is pinned. Pre-releases are evaluated in separate CI jobs.

Rules. The goals are held up by eight rules, which this RFC and the source
comments cite by number ("RFC rule 3"). They are listed in
[`../architecture.md`](../architecture.md#rules): replaceable loader
adapters (1), the core owning request semantics (2), identical behaviour on
both platforms (3), one copy of shared logic (4), no Swift/C++ interop (5),
SwiftPM and CocoaPods building the same thing (6), pinned production
dependencies (7), pre-releases evaluated apart (8).

Non-goals:

- visionOS and macOS targets (tvOS was a non-goal too until it was added on 2026-11-18, as the iOS code built for a second platform; see the compatibility matrix),
- the Old Architecture and the interop layer.

The 1.x feature set (placeholders, processors, GIF/APNG/SVG, prefetch,
cache-management APIs, progress events) was a non-goal of the toolchain
milestone this RFC started as. It was ported once the gate was met and is now
in scope: §4.2a, §4.4–§4.5c, and Phase 2 of `docs/migration-plan.md`. Six
things went beyond 1.x parity along the way, each recorded where it is
specified: `require()` sources (§4.1), the `memoryOnly` / `noCache` /
`cacheOnly` policies (§4.1), `urlCache` honouring HTTP headers on Android as
well as iOS (§4.2a), `recyclingKey` (§4.4d), the Android `User-Agent` (§4.5b),
and `allowDownscaling` (§4.5c).

### 4.1 Ownership of request semantics (rules 2 and 3)

`cpp/include/turboimage/ImageRequest.h` is the single definition of:

- **Validation**: empty URIs and unsupported schemes are rejected, and so are header names that are not RFC 9110 tokens and header values containing CR, LF or NUL (`InvalidHeader`, reported to JS as `invalidRequest`). Passing such a header on would allow header injection; dropping it silently would hide an auth bug.
- **Schemes.** Remote: `http`, `https`. Local: `file`, `content`, `android.resource`. The core doesn't know the platform, so an Android-only scheme on iOS fails in the loader (as `network`). Local sources never use the disk tier (copying a local file into the cache only costs space) and are always readable: reading one is not a network request, so `cacheOnly` still loads it. The memory tier follows the policy as usual. Both rules are applied after the policy matrix, so every policy agrees (a local source under `urlCache` has no HTTP cache either).
- **`require()` sources.** JS resolves them with RN's `Image.resolveAssetSource`, which picks the `@2x`/`@3x` file. That gives a dev-server URL in development, a `file://` bundle URL in iOS release builds, and a bare resource name (`src_assets_logo`) in Android release builds. The Android view and module map such names to `android.resource://<package>/<id>` (`SourceUris.kt`, RN's naming rule) before the core sees them, and an unknown name stays schemeless, so the core rejects it. Smoke scenario `requireAsset` loads a bundled PNG with `cacheOnly` in release builds on both platforms.
- **Headers** (`source.headers`, 1.x's record, pairs or `Headers` forms, normalised in JS to `[{name, value}]` because Codegen props can't express a dictionary): sent in order by both adapters, and by `prefetch`. They are **not** part of the cache key, as in 1.x: a URL is one entry whoever fetched it. Nor are they part of the in-flight identity: concurrent loads of one key are coalesced (Nuke task coalescing, Coil dedup) whatever their headers. Apps that serve per-user content at one URL must pass a per-user `cacheKey`, which separates both. The smoke scenarios `headersSent` / `headersChangeResponse` use the fixture server's `Accept`-dependent `/accept/png` (200 vs 406) to prove the header reaches the server, and `headerInjection` checks the rejection.
- **Cache key**: an explicit `cacheKey`, otherwise the canonical URI with the scheme and host lower-cased and the fragment dropped. Adapters use this key for **both** the memory and disk tiers (Nuke `imageID`; Coil `memoryCacheKey` + `diskCacheKey`).
- **Cache policy → tier access matrix**:

| `cachePolicy` | memory read/write | disk read/write | network |
|---|---|---|---|
| `default` | ✓ / ✓ | ✓ / ✓ | ✓ |
| `memoryOnly` | ✓ / ✓ | ✗ / ✗ | ✓ |
| `noCache` | ✗ / ✗ | ✗ / ✗ | ✓ |
| `cacheOnly` | ✓ / ✗ | ✓ / ✗ | ✗ |
| `urlCache` | ✓ / ✓ | ✓ / ✓, but of the HTTP cache (`httpCache`, §4.2a) | ✓ |

Adapters translate a `ResolvedRequest` field by field and make no policy
decisions of their own. The matrix is covered by parameterised GoogleTests.

The core also decides how large the image is decoded (`ResolvedRequest.decode`,
§4.5c).

### 4.2 Consistent cache behaviour

Each adapter needs explicit configuration so both platforms behave the same:

| Concern | iOS (Nuke) | Android (Coil) |
|---|---|---|
| Loader instance | Dedicated `ImagePipeline`, **not** `.shared` | Dedicated `ImageLoader` built on `coil-core`, **not** the `coil` singleton |
| Memory tier | Own `ImageCache()`, so `withDataCache` doesn't fall back to `ImageCache.shared` | `MemoryCache` at 25% of the app's memory |
| Disk tier | `DataCache` holding original bytes, 150 MB | `DiskCache` in `cacheDir/turboimage`, 150 MB |
| HTTP cache | Disabled for the disk tier above (`urlCache = nil`): `Cache-Control` is ignored. Only `urlCache` requests use one (§4.2a) | OkHttp has no `Cache`; `CacheStrategy.DEFAULT` serves disk hits without consulting `Cache-Control`. Only `urlCache` requests differ (§4.2a) |
| Network fetcher | `DataLoader` / `URLSession` | Explicit `OkHttpNetworkFetcherFactory` with its own `OkHttpClient` (15 s connect, 30 s read) |
| Concurrent request dedup | Task coalescing (default, set explicitly) | `DeDupeConcurrentRequestStrategy` (`@ExperimentalCoilApi`) |

Decision ([ADR 0002](../adr/0002-disk-cache-is-authoritative.md)): TurboImage's disk cache is authoritative and HTTP freshness headers
are ignored on both platforms, for every policy but one. Apps that need the
server to control freshness opt in per image with `cachePolicy="urlCache"`
(§4.2a).

Host network state. Per-request configuration is `source.headers` (§4.1), as
in 1.x. Cookies are the one piece of host state the adapters share: iOS
through `URLSessionConfiguration.default` (the shared `HTTPCookieStorage`),
Android through a `CookieJar` over React Native's `ForwardingCookieHandler`,
the store `fetch` and WebView use. The Android client takes nothing else from
the host, so the app's interceptors cannot change image loading. 1.x built
its own Android client with no cookie jar, so cookies on Android are new in
2.0. TODO: an app-wide native hook for default headers or an interceptor.

Coil's dedup strategy is experimental API. We opt in because without it,
Android would issue N network requests for N identical concurrent views where
iOS issues one. If Coil changes or removes the API, the fallback is
`ConcurrentRequestStrategy.UNCOORDINATED`, which is still correct, only less
efficient. CI compiles against the pinned version, so a source break would
show up there.

### 4.2a The HTTP cache (`cachePolicy="urlCache"`)

1.x's name. In 1.x it honoured HTTP headers on iOS only; in 2.0 it is a core
policy (`CachePolicy::UrlCache`) and does so on both platforms. The core sets
`ResolvedRequest.httpCache`, which tells the adapter that this request's disk
tier is an HTTP cache:

| | iOS (Nuke) | Android (Coil) |
|---|---|---|
| Store | A `URLCache` of TurboImage's own (150 MB, disk only), behind a second `ImagePipeline` | The same Coil `DiskCache`, under a `turboimage-http:<url>` key |
| Freshness rules | `URLSession`'s protocol cache policy | Coil's `CacheControlCacheStrategy` (`coil-network-cache-control`, `@ExperimentalCoilApi`), chosen per request by a delegating strategy |

- **Contract.** An entry is served while `Cache-Control` / `Expires` say it is fresh, is revalidated when stale (`If-None-Match`, a 304 carries no body), and is never stored for `no-store`.
- **A store of its own, keyed by URL.** HTTP caches know nothing of `cacheKey`. Nothing is read from or written to the key-addressed disk cache, so a later `cacheOnly` load does not see what a `urlCache` load stored, and the reverse. Mixing them would let a keyed read serve an expired image.
- **Why a second pipeline on iOS.** Nuke's `DataCache` sits in front of the data loader and has no notion of freshness. Not `URLCache.shared`, so the host app's networking cannot fill or clear it.
- **The memory tier is shared and unchanged**: keyed by `cacheKey`, and it never expires within a process. A list must not refetch on every scroll. So freshness is checked when an image is not in memory, not on every mount.
- **Cache module.** `dispose` and `clearDiskCache` also evict from the HTTP cache (by URL).
- **Limit (iOS).** `URLCache` does not store a response larger than 5% of its capacity, 7.5 MB here; such an image is refetched every time.
- **Tests.** The core matrix is in GoogleTest. The smoke scenario `urlCache` loads with `urlCache`, clears memory, expects `cacheOnly` to miss (`notCached`), then loads with `urlCache` again. Whether a load reached the network is not visible in the events, so each of the three scenarios then asks the fixture server what it received (§8): `urlCache` (`max-age=3600`) must have caused one request for its two loads, `urlCacheNoStore` two unconditional requests, and `urlCacheRevalidate` (`no-cache` + `ETag`) a 200 followed by a conditional 304.

### 4.3 Threading and ownership contracts

- **C++ core**: pure functions on value types. No globals and no I/O. Thread-safe and reentrant. Results own all their data.
- **JNI**: local references only, nothing cached across calls. Called on the UI thread.
- **Seams** (`TIImageLoading`, `ImageLoaderAdapter`): `load` is called on the main thread. The completion fires exactly once on the main thread, or never if the load was cancelled first. `cancel` is idempotent.
- **Views** guard against stale completions by a per-load token. This applies on top of adapter-side cancellation, because Fabric recycles views. The guard, and every other decision about what a view shows and which load events it emits, is the core's `ViewLifecycle` (`cpp/include/turboimage/ViewLifecycle.h`, [ADR 0010](../adr/0010-view-lifecycle-in-the-core.md)): a view says what happened and carries out the effects it gets back. The state is per view and used on the main thread only.

### 4.4 Error taxonomy

`onFailure` carries `{ code, error }`. `code` is the contract (new in 2.0), and `error`
keeps its 1.x name but is diagnostic text only. The core defines the codes (`turboimage::LoadErrorCode`
and `loadErrorCodeName()`), and each adapter classifies its loader's errors
into them:

| `code` | Meaning | Nuke 13 | Coil 3 |
|---|---|---|---|
| `invalidRequest` | Rejected by the core before any loader ran | — (core) | — (core) |
| `notCached` | The policy forbade the network and no cache tier had the image | `dataMissingInCache` | Synthetic HTTP 504 **and** `!allowNetwork` |
| `network` | Transport or HTTP failure | `dataLoadingFailed`, `dataIsEmpty`, `dataDownloadExceededMaximumSize` | `HttpException`, `IOException` (including a 504 while offline) |
| `decode` | Bytes arrived but no image came out | `decoderNotRegistered`, `decodingFailed`, `processingFailed` | Any other failure |
| `unknown` | Everything else, including adapter bugs | `imageRequestMissing`, `pipelineInvalidated`, non-Nuke errors | — |

Without this, a `cacheOnly` miss surfaced as `Nuke.ImagePipeline.Error error 4`
on iOS and `HTTP 504` on Android. The on-device smoke test now asserts
`notCached` on both.

### 4.4a Event lifecycle

The event names and payloads are 1.x's, so app handlers keep working. Per load:

```
onStart {state:'running'} → onProgress {completed,total}* → onSuccess {width,height,source}
                                                          | onFailure {code,error}
                         → onCompletion {state:'completed'}
```

- **Rejected requests.** A request the core rejects (`invalidRequest`) fails *before* `onStart`, because no load began. A view with no source, or an empty `uri`, is such a request: it reports `invalidRequest` when it is mounted, on both platforms. (Until the views compared whole requests, iOS stayed silent for it, and Android did for an absent source but not for an empty `uri`.)
- **When a load starts.** A view loads for its first props, and again whenever the request changes: the core's `ImageRequest` (source, cache policy, processors, `allowDownscaling`, `resizeMode`) compared as one value, plus `allowHardware` on Android. The views keep no list of their own, so a field added to the request cannot be forgotten on one platform.
- **Superseded loads.** A load superseded by a new `source` ends with `onCompletion {state:'cancelled'}` and never reports success. 1.x declared that state but never sent it.
- **Progress pacing.** Progress is paced by the core's `ProgressThrottle`: each whole percent, or every 64 KiB when `total` is unknown (`-1`). So JS sees the same cadence whether Nuke reports per chunk or OkHttp per `read()`. The throttle state is three integers, so Android keeps it in a `LongArray` passed through JNI, with no native handle.
- **Progress ends at 100%.** A successful load with a known total always ends with a `{total, total}` progress event, via `ProgressThrottle::finish`. Coil can decode a `noCache` response straight from the network stream and stop at the JPEG end marker without reading to EOF, so Android's byte count can end short. The smoke scenario `supersede` caught this intermittently.
- **Android progress.** Coil has no progress API. The adapter tags each request with a per-load token header (`X-TurboImage-Load`), which an OkHttp interceptor strips and uses to count response bytes. 1.x keyed this on the view tag, which could route an old request's progress into a view's new load.
- **Known gap.** With Coil's dedup, only the first of N identical concurrent loads reports progress on Android. Nuke reports it to all of them.
- **`onSuccess` size** is the decoded image's size in pixels, on both platforms (iOS multiplies `UIImage.size` by its scale; a vector SVG shown unprocessed has no pixels and reports its canvas). By default that is no larger than the view (§4.5c), so it is the source's intrinsic size only when the source is smaller than the view or `allowDownscaling` is off. The smoke scenarios `downscaled` and `fullSize` assert both cases with a 3000×2000 source.
- **Tests.** The smoke scenarios `lifecycle` and `supersede` assert these exact sequences on both platforms.

| `rounded` | JS clipping container | Same approach as 1.x. ### 4.4c Cache TurboModule

`TurboImage.prefetch / dispose / clearMemoryCache / clearDiskCache` are 1.x statics, now backed by a Codegen TurboModule (`TurboImageModule`, `codegenConfig.type: "all"`).

- **Same keys as views.** Every source goes through the same core resolution as a view's source: on iOS a shared ObjC++ `TIMakeImageRequest`, on Android the same JNI `resolve`. A prefetched or disposed entry is therefore exactly the one a view reads. The smoke scenarios `prefetchThenCacheOnly`, `disposeEvicts` and `clearCaches` prove this with `cacheOnly` reads.
- **One loader.** Android shares a single adapter, and so one Coil `ImageLoader`, between views and the module (`TurboImageLoaders`). iOS shares it through `TIImageLoaderRegistry`.
- **Behaviour changes from 1.x.** `prefetch` resolves `true` only if every source loaded; 1.x resolved `true` regardless. `dispose` evicts from memory and disk; 1.x declared it in JS but never implemented it natively, so calling it threw.
- **Cache-policy strings** are parsed by the core (`parseCachePolicy`) for both the module and the Android view.

### 4.4d Source changes and `recyclingKey`

New in 2.0, with the contract of expo-image's prop of the same name. It
decides what a view shows while a *new* load runs, after a request prop
(`source`, `cachePolicy`, a processor, `allowHardware`) changed:

| `recyclingKey` in that update | Shown while the new load runs |
|---|---|
| unchanged (or never set) | The previous image. The new one replaces it with the usual cross-fade, or at once on a memory-cache hit |
| changed | Nothing, or the placeholder |

- **Why both.** Keeping the previous image is right when the view still shows the same thing: a thumbnail swapped for the full photo, a processor toggled. It is wrong in a list that reuses views (FlashList), where the previous image belongs to another row. Only the app knows which case it is in, so it says so with the key, typically the row's id.
- **Behaviour change from 1.x**, which blanked the view on every load. Apps that reuse views and relied on that must now pass a `recyclingKey`.
- **Only a loaded image is kept.** A placeholder or a failed view is cleared as before, and the placeholder is not drawn over a kept image.
- **Failure.** A kept image is removed when the new load fails, because it is not what `source` names. With `showPlaceholderOnFailure` the placeholder then appears, as it would have without a previous image.
- **A key change alone does nothing.** With the request props unchanged the image on screen is already the right one, so no load starts and nothing is cleared.
- **Not a request field.** The key lives in the two views only. It never reaches request resolution, the seams or the cache keys; the core's lifecycle is told only whether it changed in the transaction that starts a load. Fabric's own view recycling on iOS still clears the view regardless (§4.6).
- **Events** are unchanged: the superseded load still ends with `onCompletion {state:'cancelled'}`.
- **Tests.** Jest covers the JS prop. TODO: the smoke test observes events, not pixels, so nothing yet checks on a device what is on screen during the second load; a screenshot taken mid-load would.

### 4.5 Placeholders (blurhash, thumbhash, memoryCacheKey)

`cpp/include/turboimage/Placeholder.h` is the only decoder, replacing four
1.x ports (Swift and Kotlin × blurhash and thumbhash).

- **Exactness.** The decoders are ports of npm `blurhash` 2.0.5 and `thumbhash` 0.1.1. GoogleTest goldens come from those references (`cpp/tests/tools/generate-placeholder-goldens.mjs`, pinned devDependencies), and the C++ output matches them **byte for byte**. That holds on macOS arm64 (Apple Clang) and on the Android arm64 emulator (NDK Clang, bionic `libm`, `scripts/test-core-android.sh`). CI adds Linux GCC, Linux Clang and Android x86_64.
- **FP contraction.** `#pragma STDC FP_CONTRACT OFF` is required. Clang fuses `a*b + c` into FMA by default on arm64, which rounds differently and would make the platforms disagree.
- **Untrusted input.** Lengths and alphabets are validated. The JS thumbhash reference reads past the end of a truncated hash; the port returns `nullopt` instead.
- **Threading.** Decoding runs on a background queue (iOS: GCD; Android: one shared single-thread executor), and the result is applied on main only if the core's lifecycle allows it: it is still the newest decode (a generation counter) and no image has taken the view since. 1.x had no such guard and could show a stale placeholder after `source` changed.
- **Lifetime.** The placeholder is shown until the image loads. On failure it is removed by default and kept only with `showPlaceholderOnFailure` (1.x's rule, §4.4b), on both platforms. Android needed a Coil target subclass so that the view decides this, because Coil's default `ImageViewTarget` sets a null image on start and on error.
- **`memoryCacheKey`.** This is a synchronous memory-cache lookup through the seam (`memoryCachedImageForKey:` / `memoryCachedDrawable`), keyed by the core's `canonicalCacheKey`, so it matches what a view stored. Coil keys memory entries by key *plus* extras (e.g. the resolved size), so the Android adapter matches on the key string across the key set.

### 4.5a Processors (resize, blur, monochrome, tint)

`cpp/include/turboimage/Processing.h` implements every processor once, as
integer arithmetic on premultiplied RGBA8. 1.x used each platform's filters
(Nuke `Resize`, `CIGaussianBlur`, `CIColorMonochrome`, `withTintColor` on iOS;
Coil 2 `coil-transformations` with RenderScript blur and `BlendMode.COLOR` on
Android), so the same props gave visibly different images, and that library
has no Coil 3 version.

| Prop | Unit / semantics | Algorithm |
|---|---|---|
| `resize` | Width in points/dp, × the screen scale (`RCTScreenScale`, `DisplayMetrics.density`). Aspect kept, never upscaled | Exact area averaging |
| `blur` | Gaussian σ in pixels of the resized image, rounded, capped at 250 | Three box blurs (Kovesi), O(pixels) for any radius, edges clamped |
| `monochrome` | Colour; Rec. 709 luma mapped onto it (`white` = greyscale). Colour alpha = intensity | Integer luma |
| `tint` | Colour, Porter-Duff source-atop (opaque area takes the colour) | Integer blend |

Order: resize → blur → monochrome → tint, as in 1.x.

- **The key is the description.** `resolveRequest` normalises the props into a `ProcessingSpec` and encodes it as `ResolvedRequest.processorKey` (`ti1;w=180;b=6;m=ffffffff`), empty when unprocessed. Adapters attach one opaque step identified by that key (Nuke `ImageProcessors.Anonymous(id:)`, a Coil `Transformation` with that `cacheKey`), and the step calls `processImage(pixels, key)`. Nothing else crosses JNI or ObjC, so the cache identity cannot disagree with the pixels. Swift can't call C++, so iOS passes the step as a block on `TIImageRequest`, built by the ObjC++ factory.
- **Caching.** `cacheKey` still names the original. Both loaders fold the processor id into the *memory* key, giving one memory entry per variant, and keep only the original on disk (Nuke `.storeOriginalData`; Coil keys disk by `diskCacheKey` alone). The smoke scenario `processed` loads a variant with `cacheOnly` from the original another view wrote. `plainAfterProcessed` checks that an unprocessed read still gets the original.
- **Dispose.** `dispose` evicts every variant. Coil matches memory keys by string, so this comes for free on Android. Nuke's memory cache can't be enumerated, so the iOS adapter records the processor keys it has seen per cache key and evicts each one. `disposeEvictsVariants` fails without that index (verified by disabling it). The `memoryCacheKey` placeholder only uses the unprocessed entry on both platforms.
- **Decode size.** With `resize`, the image is decoded at the resize width; with `blur` alone, at full size, because the radius is in image pixels and must act on the same bitmap in a small view and a large one (§4.5c).
- **Cost.** A 12 MP blur takes ~270 ms on an M-series host. It runs on the loaders' background queues. `resize` + blur on a 1200 px result takes ~50 ms.
- **Not ported.** 1.x's `rounded` also added a circle-crop processor. 2.0 clips with a container (§4.4b), so that processor is redundant. The plan's `borderRadius` processor never existed as a 1.x prop: `UIImage+BorderRadius.swift` was dead code.

### 4.5b Formats (animated GIF/APNG/WebP, SVG)

The format is detected from the bytes on both platforms, so 1.x's `format` prop is accepted and ignored.

| Format | iOS (Nuke adapter, `NukeDecoders.swift`) | Android (Coil components) |
|---|---|---|
| Animated GIF, APNG, WebP | The first frame as a still, with the animation attached; NukeUI's `AnimatedImageView` plays it from lazily decoded frames (ADR 0012). Replaces 1.x's Gifu and APNGKit pods | `AnimatedImageDecoder` (API 28+; `GifDecoder` below) for GIF/WebP; LINE `apng-drawable` 1.12.0 for APNG, which `ImageDecoder` shows as a still |
| SVG | 1.x's private CoreSVG (vector `UIImage`), now with every symbol checked so a missing one fails as `decode` instead of crashing. **Private API, kept by decision** (App Review risk) | `coil-svg` (AndroidSVG) |

- **Two Nuke details** cost a debugging round each, and the smoke screenshots caught both. (1) Nuke creates a task's decoder once, from the *first partial chunk*, and reuses it for the complete data, so the format can't be picked in `makeImageDecoder`. Every task gets a `ContentDecoder` that decides on the complete bytes and forwards previews to Nuke's default. (2) Nuke flags every completed decode for decompression, which redraws it into one bitmap. `TurboImagePipelineDelegate.shouldDecompress` exempts SVG images, which would be rasterised at their canvas size; everything else keeps background decompression. A third came with Nuke 14: its decoder attaches no animation to a request with `thumbnail` options, which nearly every TurboImage request has, so `ContentDecoder` attaches it and Nuke's own parsing is off.
- **Timing.** Per-frame delays are the file's. Delays ≤ 10 ms play at 100 ms, the browser rule Android's decoder also follows. Animations loop for as long as they are shown on both platforms, whatever loop count the file declares.
- **Accessibility (iOS only).** An animation shows a still while Reduce Motion is on or Auto-Play Animated Images is off, and pauses while its view is outside a window, hidden or transparent.
- **Memory.** Both platforms decode frames as they are shown. iOS keeps them in Nuke's frame pool (5% of the device's memory, at most 128 MB, shared by every animation on screen and between views of the same one); an animation that does not fit is decoded again on each loop. Frames are sized for the view, like the still, unless `allowDownscaling` is off. Nuke shares frames by the identity of the animation, and an image is decoded once per view size, so the adapter hands every decode of a cache key the same animation (`AnimationSources`); without that, one GIF at two sizes was two sets of frames.
- **Processors** apply to the first frame and the result is static, on both platforms (Coil converts animated results to a bitmap for transformations; 1.x Android did the same). TODO: per-frame processing.
- **User-Agent (Android).** OkHttp's default `okhttp/x` is refused by some hosts (Wikimedia answers 403; 1.x had the same problem), while iOS's CFNetwork default is accepted. The smoke scenario `userAgent` loads from a route that answers 403 to that default. The Android client now sends `<App>/<version> TurboImage/<core> (Android <release>)`; `source.headers` can override it.
- **Tests.** The smoke scenarios `gif`, `apng`, `webp` and `svg` assert loads and intrinsic sizes. Animation was verified with two screenshots a second apart on each platform. There is no event for it.

### 4.5c Decode size (`allowDownscaling`)

New in 2.0, with expo-image's prop name and default (`true`). A 12 MP photo
decoded in full for a thumbnail costs ~48 MB of bitmap for pixels nobody
sees. The core picks the target (`ResolvedRequest.decode`), in this order:

| Condition | Decoded at |
|---|---|
| `allowDownscaling={false}` | Full size |
| `resize` set | The resize width |
| `blur` without `resize`, or `resizeMode="center"` (drawn 1:1) | Full size |
| Otherwise | The view's size in pixels: covering it for `cover` / `stretch`, fitting inside it for `contain` |

- **An upper bound, never an upscale.** A source smaller than the target is decoded as it is.
- **Adapters downsample while decoding**, so the full bitmap is never allocated: Nuke thumbnail options (ImageIO) on iOS, Coil's size and scale with `Precision.INEXACT` on Android.
- **Android needed its own size resolver.** Fabric leaves views with `WRAP_CONTENT` layout params, which Coil's `ViewSizeResolver` reads as "no bound", so every image was decoded in full. `LaidOutSizeResolver` waits for the first layout and uses the laid-out size.
- **Caching.** The disk keeps the original bytes; each decode size is its own memory entry. The smoke scenario `fullSize` reads all 3000×2000 pixels with `cacheOnly` after `downscaled` loaded the same URL at the card's size.
- **The size is taken when the load starts.** A view that grows later keeps the image it has. TODO: reload when the view outgrows the decoded image; until then `allowDownscaling={false}` is the way out for zoomable views.
- **No view, no bound.** `prefetch` and a view laid out with no area decode the original.
- **SVG has no pixels to keep**, so it gets a target of its own (`ResolvedRequest.vectorDecode`): the table above without its first row. Only the loader learns from the bytes that a source is an SVG, so the core always resolves both targets.
  - *Own size.* Where the table says "full size", an SVG is drawn at its own size read as points/dp (120×80 is 315×210 px on a 2.6× screen), so `center` draws it as large on every screen and `blur` is as strong. Android: `SvgDecoder.Factory(scaleToDensity = true)`. Before, a 120×80 SVG was 120×80 px on Android, a thumbnail under `center`.
  - *`allowDownscaling={false}`* does not apply: the SVG is still drawn for the view. Its own size is usually smaller than the view, and scaling that bitmap up is what the opt-out exists to prevent (measured on Android: 315×210 stretched over 630×420). The Coil request still says `Size.ORIGINAL`, which is right if the bytes turn out to be a bitmap; `VectorSizeDecoderFactory` wraps the SVG decoder and swaps in the vector target.
  - *iOS only needs this with a processor.* A vector `UIImage` is sharp at any size while the view draws it. The core's processors work on pixels, and the seam's processor used to draw the vector at its canvas size at 1× (120×80 px for a 720×480 px view, so `blur` was about 2.6× stronger than on Android and `tint` was coarse). The Nuke adapter now draws it at `TIImageRequest.vectorDecodeSize` first, capped at 4096 px a side, Coil's `maxBitmapSize`.
  - *Trade-off.* With `allowDownscaling={false}` and a processor, Nuke's memory key carries no size (the request has no thumbnail bound), so the same processed SVG shown in two views of different sizes shares the entry the first one drew. On Android, Coil does not reuse a vector's bitmap for an original-size request at all and draws it again from the disk bytes. Both are narrow; neither is handled.
  - *Tests.* Core: `ResolveVectorDecodeSize.*`. Smoke: `svgFullSize`, `svgTinted`, `svgFullSizeTinted`, `svgBlurred` assert the drawn sizes on both platforms. `center` has no scenario (the smoke cards are all `cover`); it was compared in screenshots of a temporary screen.
- **`onSuccess`** reports the decoded size (§4.4a).

### 4.6 View-level fixes found by the smoke test

- **iOS recycling.** Fabric doesn't reset `_props` in `prepareForRecycle`, and it remounts a recycled view with `oldProps:nullptr`. Because the view diffs against `_props`, a recycled view given its previous source never reloaded and stayed blank. `prepareForRecycle` now resets `_props` to defaults. The smoke scenario `recycledSameSource` failed (timed out) before the fix and passes after it.
- **Android clipping.** Fabric's `ReactViewGroup` sets `clipChildren=false`, and `ImageView` doesn't clip its own drawable, so `cover` images whose aspect differs from the view painted over their neighbours. `cropToPadding = true` is the Android counterpart of iOS `clipsToBounds`.

### 4.7 iOS module layout (rules 5 and 6)

| SwiftPM target | Language | Path | Depends on | Owner |
|---|---|---|---|---|
| `TurboImageCore` | C++20 | `cpp/` | — | core |
| `TurboImageLoaderAPI` | ObjC | `ios/LoaderAPI` | UIKit | core (seam) |
| `TurboImageNuke` | Swift 6 | `ios/Nuke` | LoaderAPI, Nuke | iOS adapter |
| `TurboImageLiveText` | Swift 6 | `ios/LiveText` | LoaderAPI, VisionKit | Live Text |
| `TurboImage` | ObjC++ | `ios/Fabric` | Core, LoaderAPI, TurboImageNuke, React products | RN integration |

Rules:

- **Public API**: the public headers are `ios/LoaderAPI/include/*.h`, which are plain ObjC. No Nuke type and no C++ type appears in them or in the JS API. Under SwiftPM the Fabric target must name a public-headers directory, so its two plain-ObjC class headers sit in `ios/Fabric/include`; `TIRequestFactory.h`, which speaks C++, stays next to the sources and private. The podspec keeps all three private, so the two paths still differ by those two ObjC headers.
- **No Swift/C++ interop**: Swift never imports C++. The ObjC++ view converts core results into `TIImageRequest`. This avoids `-cxx-interoperability-mode`, which would spread to every target that imports the Swift module.
- **Adapter lookup by name** ([ADR 0003](../adr/0003-plain-objc-seam-on-ios.md)): `TIImageLoaderRegistry` finds the default adapter with `NSClassFromString(@"TurboImageNukeLoader")`. Importing the Swift adapter from the seam would invert the layering and create a SwiftPM cycle. The trade-off is that a name typo fails at runtime, not at link time; the example app exercises this lookup in CI. Apps can replace the adapter with `TIImageLoaderRegistry.sharedLoader = …`.
- **CocoaPods equivalence**: `TurboImage.podspec` compiles the same five trees into one pod. The sources are written to work under both: `#if canImport(TurboImageLoaderAPI)`, quoted seam includes, and `cpp/include` on the header search path. Swift 6 mode, C++20 and the Nuke tag are the same in both.

### 4.8 Android layout

- `android/CMakeLists.txt` does `add_subdirectory(../cpp)` and links `turboimage_core` into `libturboimage.so` alongside a JNI bridge. There is no Android copy of the C++ (rule 4). The `.so` is linked with 16 KB page alignment.
- Kotlin: `TurboImageViewManager` implements the Codegen `TurboImageViewManagerInterface`. `TurboImageView` takes the same steps as the iOS view, decided by the same core lifecycle. `ImageLoaderAdapter` is the seam, and the `Coil*.kt` files in `loader/` are the only Coil-aware code. An app replaces the adapter with `TurboImageLoaders.set`.
- **The seam is not the iOS seam's shape.** The Android adapter is handed the `ImageView` and displays the image itself (cross-fade, animated playback, waiting for layout before sizing the decode); the iOS adapter returns a `UIImage` and the view displays it. [ADR 0004](../adr/0004-android-adapter-displays-the-image.md) records why and what it costs.
- **Coil and the view's attach state** (read from Coil's source; the smoke test is consistent with it). With `target(ImageView)`, Coil:
  - cancels a request that starts before the view is attached and restarts it on attach (Fabric applies props before mounting),
  - disposes on detach and restarts on reattach,
  - stops restarting after our explicit `dispose()`.

  Android Fabric only recycles views for managers that call `setupViewRecycling()`, and TurboImage doesn't. Coil also restarts a request that has already completed, and its target repaints whatever the view's own guards say. So the adapter disposes each request as soon as it succeeds or fails, and only an in-flight load is ever restarted: `onSuccess` fires once per request, a failed load is not retried behind the view's back, and a `noCache` source is not downloaded again on reattach. TODO: a long, fast-scrolling list stress test before enabling recycling.
- **Coil and the Activity lifecycle.** Fabric builds each `ThemedReactContext` on top of the root view's context, which is the Activity (`FabricUIManager.startSurface`). Coil's `getLifecycle()` walks the `ContextWrapper` chain, so it finds the Activity. Requests therefore wait for `STARTED` and are disposed on `ON_DESTROY`, without TurboImage doing anything.
- R8: `consumer-rules.pro` keeps the classes and constructors that JNI creates by name. The example's release build has R8 enabled, and CI asserts that those classes survive unrenamed.

### 4.9 C++ core build

`cpp/CMakeLists.txt` is the only build description for the core. It has three consumers:

1. A host build with GoogleTest (`TURBOIMAGE_BUILD_TESTS=ON`).
2. Android, via `add_subdirectory`.
3. iOS, where `Package.swift` and the podspec compile the same `src/` and `include/` trees directly. iOS does not use CMake, so a new compile definition must be mirrored in both iOS manifests. The header comment in `cpp/CMakeLists.txt` says so.

## 5. Monorepo layout

```
v2/
  package.json  bunfig.toml  bun.lock
  packages/react-native-turbo-image/   npm package (JS + iOS + Android + cpp)
    src/  cpp/  ios/{LoaderAPI,Nuke,LiveText,Fabric,vendor*}  android/
    Package.swift  TurboImage.podspec  package.json
  apps/example/                        RN 0.88.1 app (CocoaPods by default)
  scripts/native-versions.env  check-native-versions.sh  build-nuke-xcframework.sh
  docs/
```

\* `ios/vendor/{Nuke,NukeUI}.xcframework` are gitignored. They are built from the pinned tag
by `scripts/build-nuke-xcframework.sh` and shipped in the npm tarball.

The core lives **inside** the npm package rather than in a separate
`@turbo-image/core` workspace. Three things require the sources to be on disk
in the published package: SwiftPM forbids target paths outside the package
root, CocoaPods needs sources under the podspec's directory, and the Android
Gradle build compiles from `node_modules`. A separate workspace would force
copying or symlinking at publish time, which is the duplication rule 4
forbids.

Bun uses the **hoisted** linker (`bunfig.toml`). RN's Gradle plugin, Metro,
Codegen and CocoaPods' node lookups assume a flat `node_modules`, and Bun 1.3
defaults new workspaces to isolated installs. The example app's Gradle and
Metro configs point at `v2/node_modules`, including an explicit
`hermesCommand`. Without it, release bundling can't find `hermes-compiler`.

## 6. Key findings that shaped the design

### 6.1 Nuke is not on CocoaPods trunk

The last Nuke release on trunk is 9.5.0, and 1.x vendored a hand-built Nuke
12.8.0. To keep CocoaPods support while pinning a current Nuke (rules 6 and 7),
CocoaPods builds use an xcframework built reproducibly from the same tag that
SwiftPM resolves. `Nuke.version` records which tag it came from, and the
version check verifies it.

### 6.2 Coil 3.6.3 requires Kotlin ≥ 2.3 in the app

Coil 3.6.3 is compiled with Kotlin 2.4.10. A Kotlin compiler reads metadata at
most one minor version ahead of itself, so RN 0.88's default of 2.2.0 cannot
consume it. RN 0.89 moves to Kotlin 2.3.21, which would be enough. Decisions:

- The example app pins `kotlinVersion = "2.4.21"`. Verified: the debug and R8 release builds pass and run on an emulator.
- The library's `build.gradle` checks the app's Kotlin version and fails early with an actionable message if it is below 2.3.
- Library Kotlin sources must stay compilable by 2.3. They use no 2.4-only language features.

### 6.3 React Native SwiftPM integration

See `docs/spm-assessment.md`. In short, RN 0.88's `npx react-native spm` works
with our hand-written `Package.swift` (verified: Debug simulator build, app
runs). However, the manifest has to point at React Native through paths
relative to the app's build directory, and the tooling is marked preview. So
**CocoaPods stays the default** for 2.0.0, and SPM is a supported opt-in
backed by a non-blocking CI job.

## 7. Dependency policy (rules 7 and 8)

- Production manifests pin exact versions: `exact:` in SwiftPM, a literal in Gradle, a tag in CMake.
- Pre-releases are only reachable through explicit evaluation switches, never through version ranges. `TURBOIMAGE_EVAL_NUKE_VERSION` is read by `Package.swift`; Nuke 14 was evaluated through it from beta to `14.0.0-rc.1` before it was pinned.
- Each evaluation runs as a `continue-on-error` CI job, and its results are written up in `docs/compatibility-matrix.md`.

`ios-cocoapods` and `android (release)` also run the on-device smoke test
(`scripts/smoke-{ios,android}.sh`) against release builds with cold caches.

Every remote fixture comes from `scripts/fixture-server.py`, which the smoke
scripts start on the host (Python 3, standard library only). The simulator
shares the host's loopback; the emulator reaches it through `adb reverse`, so
both platforms load the same `http://localhost:8765` URLs.

- **Why local.** The suite used to load from six third-party hosts. A slow or changed host looked like a product bug, and a public host cannot answer by request header, send chosen `Cache-Control` headers, send slowly on purpose, or say how many requests arrived.
- **Fixtures** are generated by `scripts/generate-fixtures.py` and committed (`apps/example/fixtures/`, about 410 KB), so the repository carries no third-party artwork and every asserted size is stated in one place.
- **Trade-off: no TLS.** The suite no longer makes an HTTPS request. TLS is the platform's, not TurboImage's, but a regression in how the adapters configure their HTTP clients for HTTPS would now go unseen. TODO: one opt-in scenario against a real host.
- **Cleartext.** The Android example allows cleartext HTTP to `localhost` and `10.0.2.2` only (`network_security_config.xml`); iOS already allows local networking.

Each run must report `TURBOIMAGE_SMOKE {"pass":true,…}`. The 49 scenarios in
`apps/example/App.tsx` cover:

- a network load,
- a `cacheOnly` hit through the canonical key (upper-case host, fragment),
- a `cacheOnly` miss (`notCached`),
- an explicit `cacheKey` shared across two different URLs,
- `noCache`,
- core validation (`invalidRequest`),
- a recycled view reloading the same source,
- a view detached and reattached: a loaded `noCache` image is not fetched again, and a failed load is not retried,
- every visible row of a `FlatList` loading,
- memory-cache hits on a mounted view giving one completion per start,
- the event lifecycle,
- a superseded load ending as `cancelled`,
- the placeholder being removed on failure by default,
- the 1.x `dataCache` name together with `rounded`,
- the `memoryCacheKey` placeholder,
- the cache module: prefetch then `cacheOnly`, dispose, clearing both tiers, and prefetch of an invalid source,
- processors: a processed variant read with `cacheOnly` from another view's original, a plain read after a processed one, and dispose evicting every variant,
- Live Text (iOS; a plain load on Android),
- request headers: sent, changing the response, and an injection attempt rejected,
- formats: GIF, APNG, animated WebP and SVG,
- SVG draw size: not shrunk to its own size by `allowDownscaling={false}`, drawn at the card size before a processor runs (with and without downscaling), drawn again for a smaller view, and blurred at its own size when nothing resizes it,
- a `require()` asset under `cacheOnly`,
- `allowHardware={false}`,
- decode size: a 3000×2000 source decoded at the card's size, then in full with `allowDownscaling={false}` from the disk original, and a 1500×1000 animated GIF decoded at the card's size,
- `urlCache`: stored in the HTTP cache, where `cacheOnly` cannot see it, and the requests the server received for a fresh, a `no-store` and a revalidated response,
- the Android `User-Agent`,
- a cookie set through React Native's `fetch` being sent with the image request,
- the indicator chaining the app's own `onStart` / `onCompletion` handlers.

The result line is compact (`passed`, `total`, failures only), because iOS `os_log` truncates messages at about 1 KB.

Three of the failing scenarios set `showPlaceholderOnFailure` and carry a blurhash, thumbhash or `memoryCacheKey` placeholder, which must stay visible; a fourth leaves the prop off and must end blank (`SMOKE_SCREENSHOT=…`). The Android job also runs the core goldens on the emulator (`scripts/test-core-android.sh`).
