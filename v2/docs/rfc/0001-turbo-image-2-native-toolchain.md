# RFC 0001: TurboImage 2.0 native toolchain and architecture

- Status: Draft. The walking skeleton builds and runs on both platforms.
- Date: 2026-11-16
- Supersedes: the 1.x layout at the repository root (`ios/`, `android/`, `src/`)

## 1. Summary

TurboImage 2.0 is a New Architecture-only rewrite. It has four parts:

- a **C++20 core** that owns request semantics and is shared by iOS and Android,
- a **Fabric component** generated by Codegen,
- **replaceable loader adapters**: Nuke 13.2.3 on iOS and Coil 3.6.3 on Android,
- a **Bun-workspace monorepo** under `v2/` that builds with SwiftPM (or CocoaPods), Gradle and CMake.

This RFC fixes the toolchain baseline and the module boundaries. It does not
design the full image pipeline. Pipeline work starts only after the minimal
example builds on both platforms, a gate that has now been met (§9).

## 2. Goals and non-goals

Goals:

1. Identical request semantics on both platforms: cache keys, cache tiers and validation.
2. Nuke and Coil can be swapped without touching JS or Fabric code.
3. SwiftPM is the preferred iOS integration, and CocoaPods behaves the same during the migration.
4. Every production dependency is pinned. Pre-releases are evaluated in separate CI jobs.

Non-goals for this milestone (TODO, pipeline milestone):

- the 1.x feature set: placeholders (blurhash/thumbhash), processors, GIF/APNG/SVG, prefetch, cache-management APIs, progress events,
- tvOS, visionOS and macOS targets,
- the Old Architecture and the interop layer.

### 4.1 Ownership of request semantics (rules 2 and 3)

`cpp/include/turboimage/ImageRequest.h` is the single definition of:

- **Validation**: empty URIs and unsupported schemes are rejected (only http/https in the skeleton).
- **Cache key**: an explicit `cacheKey`, otherwise the canonical URI with the scheme and host lower-cased and the fragment dropped. Adapters use this key for **both** the memory and disk tiers (Nuke `imageID`; Coil `memoryCacheKey` + `diskCacheKey`).
- **Cache policy → tier access matrix**:

| `cachePolicy` | memory read/write | disk read/write | network |
|---|---|---|---|
| `default` | ✓ / ✓ | ✓ / ✓ | ✓ |
| `memoryOnly` | ✓ / ✓ | ✗ / ✗ | ✓ |
| `noCache` | ✗ / ✗ | ✗ / ✗ | ✓ |
| `cacheOnly` | ✓ / ✗ | ✓ / ✗ | ✗ |

Adapters translate a `ResolvedRequest` field by field and make no policy
decisions of their own. The matrix is covered by parameterised GoogleTests.

### 4.2 Consistent cache behaviour

Each adapter needs explicit configuration so both platforms behave the same:

| Concern | iOS (Nuke) | Android (Coil) |
|---|---|---|
| Loader instance | Dedicated `ImagePipeline`, **not** `.shared` | Dedicated `ImageLoader` built on `coil-core`, **not** the `coil` singleton |
| Memory tier | Own `ImageCache()`, so `withDataCache` doesn't fall back to `ImageCache.shared` | `MemoryCache` at 25% of the app's memory |
| Disk tier | `DataCache` holding original bytes, 150 MB | `DiskCache` in `cacheDir/turboimage`, 150 MB |
| HTTP cache | Disabled (`urlCache = nil`). `Cache-Control` is ignored | OkHttp has no `Cache`; `CacheStrategy.DEFAULT` serves disk hits without consulting `Cache-Control` |
| Network fetcher | `DataLoader` / `URLSession` | Explicit `OkHttpNetworkFetcherFactory` with its own `OkHttpClient` (15 s connect, 30 s read) |
| Concurrent request dedup | Task coalescing (default, set explicitly) | `DeDupeConcurrentRequestStrategy` (`@ExperimentalCoilApi`) |

Decision: TurboImage's disk cache is authoritative and HTTP freshness headers
are ignored on both platforms. That matches 1.x and is the only policy both
loaders support identically today. A `respectHttpHeaders` mode, which would
need Coil's `coil-network-cache-control` and a `URLCache`-backed Nuke
configuration, is a TODO.

Coil's dedup strategy is experimental API. We opt in because without it,
Android would issue N network requests for N identical concurrent views where
iOS issues one. If Coil changes or removes the API, the fallback is
`ConcurrentRequestStrategy.UNCOORDINATED`, which is still correct, only less
efficient. CI compiles against the pinned version, so a source break would
show up there.

### 4.3 Threading and ownership contracts

- **C++ core**: pure functions on value types. No globals and no I/O. Thread-safe and reentrant. Results own all their data.
- **JNI**: local references only, nothing cached across calls. Called on the UI thread.
- **Seams** (`TIImageLoading`, `ImageLoaderAdapter`): `load` is called on the main thread. The completion fires exactly once on the main thread, or never if the load was cancelled first. `cancel` is idempotent.
- **Views** guard against stale completions by handle identity. This applies on top of adapter-side cancellation, because Fabric recycles views.

### 4.4 Error taxonomy

`onFailure` carries `{ code, error }`. `code` is the contract (new in 2.0), and `error`
keeps its 1.x name but is diagnostic text only. The core defines the codes (`turboimage::LoadErrorCode`
and `loadErrorCodeName()`), and each adapter classifies its loader's errors
into them:

| `code` | Meaning | Nuke 13 | Coil 3 |
|---|---|---|---|
| `invalidRequest` | Rejected by the core before any loader ran | — (core) | — (core) |
| `notCached` | The policy forbade the network and no cache tier had the image | `dataMissingInCache` | Synthetic HTTP 504 **and** `!allowNetwork` |
| `network` | Transport or HTTP failure | `dataLoadingFailed`, `dataIsEmpty`, `dataDownloadExceededMaximumSize` | `HttpException`, `IOException` (including a 504 while offline) |
| `decode` | Bytes arrived but no image came out | `decoderNotRegistered`, `decodingFailed`, `processingFailed` | Any other failure |
| `unknown` | Everything else, including adapter bugs | `imageRequestMissing`, `pipelineInvalidated`, non-Nuke errors | — |

Without this, a `cacheOnly` miss surfaced as `Nuke.ImagePipeline.Error error 4`
on iOS and `HTTP 504` on Android. The on-device smoke test now asserts
`notCached` on both.

### 4.4a Event lifecycle

The event names and payloads are 1.x's, so app handlers keep working. Per load:

```
onStart {state:'running'} → onProgress {completed,total}* → onSuccess {width,height,source}
                                                          | onFailure {code,error}
                         → onCompletion {state:'completed'}
```

- **Rejected requests.** A request the core rejects (`invalidRequest`) fails *before* `onStart`, because no load began.
- **Superseded loads.** A load superseded by a new `source` ends with `onCompletion {state:'cancelled'}` and never reports success. 1.x declared that state but never sent it.
- **Progress pacing.** Progress is paced by the core's `ProgressThrottle`: each whole percent, or every 64 KiB when `total` is unknown (`-1`). So JS sees the same cadence whether Nuke reports per chunk or OkHttp per `read()`. The throttle state is three integers, so Android keeps it in a `LongArray` passed through JNI, with no native handle.
- **Progress ends at 100%.** A successful load with a known total always ends with a `{total, total}` progress event, via `ProgressThrottle::finish`. Coil can decode a `noCache` response straight from the network stream and stop at the JPEG end marker without reading to EOF, so Android's byte count can end short. The smoke scenario `supersede` caught this intermittently.
- **Android progress.** Coil has no progress API. The adapter tags each request with a per-load token header (`X-TurboImage-Load`), which an OkHttp interceptor strips and uses to count response bytes. 1.x keyed this on the view tag, which could route an old request's progress into a view's new load.
- **Known gap.** With Coil's dedup, only the first of N identical concurrent loads reports progress on Android. Nuke reports it to all of them.
- **Tests.** The smoke scenarios `lifecycle` and `supersede` assert these exact sequences on both platforms.

### 4.4b 1.x prop compatibility

| 1.x prop | 2.0 | Notes |
|---|---|---|
| `resizeMode` default `contain` | Spec default `contain` | React Native's `<Image>` defaults to `cover`; kept as `contain` so 1.x layouts don't change |
| `cachePolicy` `'dataCache'` | Mapped to `'default'` in JS | Same behaviour (RFC §4.2); warns in development |
| `cachePolicy` `'urlCache'` | Mapped to `'default'` in JS | **Behaviour differs**: HTTP `Cache-Control` is no longer honoured; warns in development |
| `showPlaceholderOnFailure` (default `false`) | Native prop, same default | When false, the placeholder is removed on failure, including a decode that finishes after the failure |
| `fadeDuration` (default 300 ms) | Native prop, same default | Skipped for memory-cache hits on both platforms: Coil's crossfade rule, mirrored on iOS through a `fromMemoryCache` flag on the seam completion |
| `rounded` | JS clipping container | Same approach as 1.x. Android's `ImageView` content isn't clipped by RN's border drawing, so a container keeps both platforms identical |

### 4.4c Cache TurboModule

`TurboImage.prefetch / dispose / clearMemoryCache / clearDiskCache` are 1.x statics, now backed by a Codegen TurboModule (`TurboImageModule`, `codegenConfig.type: "all"`).

- **Same keys as views.** Every source goes through the same core resolution as a view's source: on iOS a shared ObjC++ `TIMakeImageRequest`, on Android the same JNI `resolve`. A prefetched or disposed entry is therefore exactly the one a view reads. The smoke scenarios `prefetchThenCacheOnly`, `disposeEvicts` and `clearCaches` prove this with `cacheOnly` reads.
- **One loader.** Android shares a single adapter, and so one Coil `ImageLoader`, between views and the module (`TurboImageLoaders`). iOS shares it through `TIImageLoaderRegistry`.
- **Behaviour changes from 1.x.** `prefetch` resolves `true` only if every source loaded; 1.x resolved `true` regardless. `dispose` evicts from memory and disk; 1.x declared it in JS but never implemented it natively, so calling it threw.
- **Cache-policy strings** are parsed by the core (`parseCachePolicy`) for both the module and the Android view.

### 4.5 Placeholders (blurhash, thumbhash, memoryCacheKey)

`cpp/include/turboimage/Placeholder.h` is the only decoder, replacing four
1.x ports (Swift and Kotlin × blurhash and thumbhash).

- **Exactness.** The decoders are ports of npm `blurhash` 2.0.5 and `thumbhash` 0.1.1. GoogleTest goldens come from those references (`cpp/tests/tools/generate-placeholder-goldens.mjs`, pinned devDependencies), and the C++ output matches them **byte for byte**. That holds on macOS arm64 (Apple Clang) and on the Android arm64 emulator (NDK Clang, bionic `libm`, `scripts/test-core-android.sh`). CI adds Linux GCC and Android x86_64.
- **FP contraction.** `#pragma STDC FP_CONTRACT OFF` is required. Clang fuses `a*b + c` into FMA by default on arm64, which rounds differently and would make the platforms disagree.
- **Untrusted input.** Lengths and alphabets are validated. The JS thumbhash reference reads past the end of a truncated hash; the port returns `nullopt` instead.
- **Threading.** Decoding runs on a background queue (iOS: GCD; Android: one shared single-thread executor), and the result is applied on main behind a generation counter plus a "final image shown" flag. 1.x had no such guard and could show a stale placeholder after `source` changed.
- **Lifetime.** The placeholder is shown until the image loads and **kept on failure**, on both platforms. Android needed a Coil target subclass for this, because Coil's default `ImageViewTarget` sets a null image on start and on error.
- **`memoryCacheKey`.** This is a synchronous memory-cache lookup through the seam (`memoryCachedImageForKey:` / `memoryCachedDrawable`), keyed by the core's `canonicalCacheKey`, so it matches what a view stored. Coil keys memory entries by key *plus* extras (e.g. the resolved size), so the Android adapter matches on the key string across the key set.

### 4.5a Processors (resize, blur, monochrome, tint)

`cpp/include/turboimage/Processing.h` implements every processor once, as
integer arithmetic on premultiplied RGBA8. 1.x used each platform's filters
(Nuke `Resize`, `CIGaussianBlur`, `CIColorMonochrome`, `withTintColor` on iOS;
Coil 2 `coil-transformations` with RenderScript blur and `BlendMode.COLOR` on
Android), so the same props gave visibly different images, and that library
has no Coil 3 version.

| Prop | Unit / semantics | Algorithm |
|---|---|---|
| `resize` | Width in points/dp, × the screen scale (`RCTScreenScale`, `DisplayMetrics.density`). Aspect kept, never upscaled | Exact area averaging |
| `blur` | Gaussian σ in pixels of the resized image, rounded, capped at 250 | Three box blurs (Kovesi), O(pixels) for any radius, edges clamped |
| `monochrome` | Colour; Rec. 709 luma mapped onto it (`white` = greyscale). Colour alpha = intensity | Integer luma |
| `tint` | Colour, Porter-Duff source-atop (opaque area takes the colour) | Integer blend |

Order: resize → blur → monochrome → tint, as in 1.x.

- **The key is the description.** `resolveRequest` normalises the props into a `ProcessingSpec` and encodes it as `ResolvedRequest.processorKey` (`ti1;w=180;b=6;m=ffffffff`), empty when unprocessed. Adapters attach one opaque step identified by that key (Nuke `ImageProcessors.Anonymous(id:)`, a Coil `Transformation` with that `cacheKey`), and the step calls `processImage(pixels, key)`. Nothing else crosses JNI or ObjC, so the cache identity cannot disagree with the pixels. Swift can't call C++, so iOS passes the step as a block on `TIImageRequest`, built by the ObjC++ factory.
- **Caching.** `cacheKey` still names the original. Both loaders fold the processor id into the *memory* key, giving one memory entry per variant, and keep only the original on disk (Nuke `.storeOriginalData`; Coil keys disk by `diskCacheKey` alone). The smoke scenario `processed` loads a variant with `cacheOnly` from the original another view wrote. `plainAfterProcessed` checks that an unprocessed read still gets the original.
- **Dispose.** `dispose` evicts every variant. Coil matches memory keys by string, so this comes for free on Android. Nuke's memory cache can't be enumerated, so the iOS adapter records the processor keys it has seen per cache key and evicts each one. `disposeEvictsVariants` fails without that index (verified by disabling it). The `memoryCacheKey` placeholder only uses the unprocessed entry on both platforms.
- **Decode size.** Processed loads decode the original on both platforms. Coil would otherwise decode at the view's size, so `blur` (in image pixels) would act on a different bitmap than on iOS. TODO: decode-time downsampling to the `resize` width on both platforms.
- **Cost.** A 12 MP blur takes ~270 ms on an M-series host. It runs on the loaders' background queues. `resize` + blur on a 1200 px result takes ~50 ms.
- **Not ported.** 1.x's `rounded` also added a circle-crop processor. 2.0 clips with a container (§4.4b), so that processor is redundant. The plan's `borderRadius` processor never existed as a 1.x prop: `UIImage+BorderRadius.swift` was dead code.

### 4.6 View-level fixes found by the smoke test

- **iOS recycling.** Fabric doesn't reset `_props` in `prepareForRecycle`, and it remounts a recycled view with `oldProps:nullptr`. Because the view diffs against `_props`, a recycled view given its previous source never reloaded and stayed blank. `prepareForRecycle` now resets `_props` to defaults. The smoke scenario `recycledSameSource` failed (timed out) before the fix and passes after it.
- **Android clipping.** Fabric's `ReactViewGroup` sets `clipChildren=false`, and `ImageView` doesn't clip its own drawable, so `cover` images whose aspect differs from the view painted over their neighbours. `cropToPadding = true` is the Android counterpart of iOS `clipsToBounds`.

### 4.7 iOS module layout (rules 5 and 6)

| SwiftPM target | Language | Path | Depends on | Owner |
|---|---|---|---|---|
| `TurboImageCore` | C++20 | `cpp/` | — | core |
| `TurboImageLoaderAPI` | ObjC | `ios/LoaderAPI` | UIKit | core (seam) |
| `TurboImageNuke` | Swift 6 | `ios/Nuke` | LoaderAPI, Nuke | iOS adapter |
| `TurboImage` | ObjC++ | `ios/Fabric` | Core, LoaderAPI, TurboImageNuke, React products | RN integration |

Rules:

- **Public API**: the only public headers are `ios/LoaderAPI/include/*.h`, which are plain ObjC. No Nuke type and no C++ type appears in any public header or in the JS API.
- **No Swift/C++ interop**: Swift never imports C++. The ObjC++ view converts core results into `TIImageRequest`. This avoids `-cxx-interoperability-mode`, which would spread to every target that imports the Swift module.
- **Adapter lookup by name**: `TIImageLoaderRegistry` finds the default adapter with `NSClassFromString(@"TurboImageNukeLoader")`. Importing the Swift adapter from the seam would invert the layering and create a SwiftPM cycle. The trade-off is that a name typo fails at runtime, not at link time; the example app exercises this lookup in CI. Apps can replace the adapter with `TIImageLoaderRegistry.sharedLoader = …`.
- **CocoaPods equivalence**: `TurboImage.podspec` compiles the same four trees into one pod. The sources are written to work under both: `#if canImport(TurboImageLoaderAPI)`, quoted seam includes, and `cpp/include` on the header search path. Swift 6 mode, C++20 and the Nuke tag are the same in both.

### 4.8 Android layout

- `android/CMakeLists.txt` does `add_subdirectory(../cpp)` and links `turboimage_core` into `libturboimage.so` alongside a JNI bridge. There is no Android copy of the C++ (rule 4). The `.so` is linked with 16 KB page alignment.
- Kotlin: `TurboImageViewManager` implements the Codegen `TurboImageViewManagerInterface`. `TurboImageView` follows the same steps as the iOS view. `ImageLoaderAdapter` is the seam and `CoilImageLoaderAdapter` the only Coil-aware file.
- R8: `consumer-rules.pro` keeps the classes and constructors that JNI creates by name. The example's release build has R8 enabled, and CI asserts that those classes survive unrenamed.

### 4.9 C++ core build

`cpp/CMakeLists.txt` is the only build description for the core. It has three consumers:

1. A host build with GoogleTest (`TURBOIMAGE_BUILD_TESTS=ON`).
2. Android, via `add_subdirectory`.
3. iOS, where `Package.swift` and the podspec compile the same `src/` and `include/` trees directly. iOS does not use CMake, so a new compile definition must be mirrored in both iOS manifests. The header comment in `cpp/CMakeLists.txt` says so.

## 5. Monorepo layout

```
v2/
  package.json  bunfig.toml  bun.lock
  packages/react-native-turbo-image/   npm package (JS + iOS + Android + cpp)
    src/  cpp/  ios/{LoaderAPI,Nuke,Fabric,vendor*}  android/
    Package.swift  TurboImage.podspec  package.json
  apps/example/                        RN 0.88.1 app (CocoaPods by default)
  scripts/native-versions.env  check-native-versions.sh  build-nuke-xcframework.sh
  docs/
```

\* `ios/vendor/Nuke.xcframework` is gitignored. It is built from the pinned tag
by `scripts/build-nuke-xcframework.sh` and shipped in the npm tarball.

The core lives **inside** the npm package rather than in a separate
`@turbo-image/core` workspace. Three things require the sources to be on disk
in the published package: SwiftPM forbids target paths outside the package
root, CocoaPods needs sources under the podspec's directory, and the Android
Gradle build compiles from `node_modules`. A separate workspace would force
copying or symlinking at publish time, which is the duplication rule 4
forbids.

Bun uses the **hoisted** linker (`bunfig.toml`). RN's Gradle plugin, Metro,
Codegen and CocoaPods' node lookups assume a flat `node_modules`, and Bun 1.3
defaults new workspaces to isolated installs. The example app's Gradle and
Metro configs point at `v2/node_modules`, including an explicit
`hermesCommand`. Without it, release bundling can't find `hermes-compiler`.

## 6. Key findings that shaped the design

### 6.1 Nuke is not on CocoaPods trunk

The last Nuke release on trunk is 9.5.0, and 1.x vendored a hand-built Nuke
12.8.0. To keep CocoaPods support while pinning 13.2.3 (rules 6 and 7),
CocoaPods builds use an xcframework built reproducibly from the same tag that
SwiftPM resolves. `Nuke.version` records which tag it came from, and the
version check verifies it.

### 6.2 Coil 3.6.3 requires Kotlin ≥ 2.3 in the app

Coil 3.6.3 is compiled with Kotlin 2.4.10. A Kotlin compiler reads metadata at
most one minor version ahead of itself, so RN 0.88's default of 2.2.0 cannot
consume it. RN 0.89 moves to Kotlin 2.3.21, which would be enough. Decisions:

- The example app pins `kotlinVersion = "2.4.21"`. Verified: the debug and R8 release builds pass and run on an emulator.
- The library's `build.gradle` checks the app's Kotlin version and fails early with an actionable message if it is below 2.3.
- Library Kotlin sources must stay compilable by 2.3. They use no 2.4-only language features.

### 6.3 React Native SwiftPM integration

See `docs/spm-assessment.md`. In short, RN 0.88's `npx react-native spm` works
with our hand-written `Package.swift` (verified: Debug simulator build, app
runs). However, the manifest has to point at React Native through paths
relative to the app's build directory, and the tooling is marked preview. So
**CocoaPods stays the default** for 2.0.0, and SPM is a supported opt-in
backed by a non-blocking CI job.

## 7. Dependency policy (rules 7 and 8)

- Production manifests pin exact versions: `exact:` in SwiftPM, a literal in Gradle, a tag in CMake.
- Pre-releases are only reachable through explicit evaluation switches, never through version ranges. `TURBOIMAGE_EVAL_NUKE_VERSION` is read by `Package.swift`, and Nuke 14 also raises the iOS floor to 16.0.
- Each evaluation runs as a `continue-on-error` CI job, and its results are written up in `docs/compatibility-matrix.md`.

`ios-cocoapods` and `android (release)` also run the on-device smoke test
(`scripts/smoke-{ios,android}.sh`) against release builds with cold caches.
Each run must report `TURBOIMAGE_SMOKE {"pass":true,…}`. The 17 scenarios in
`apps/example/App.tsx` cover:

- a network load,
- a `cacheOnly` hit through the canonical key (upper-case host, fragment),
- a `cacheOnly` miss (`notCached`),
- an explicit `cacheKey` shared across two different URLs,
- `noCache`,
- core validation (`invalidRequest`),
- a recycled view reloading the same source,
- the event lifecycle,
- a superseded load ending as `cancelled`,
- the placeholder being removed on failure by default,
- the 1.x `dataCache` name together with `rounded`,
- the `memoryCacheKey` placeholder,
- the cache module: prefetch then `cacheOnly`, dispose, clearing both tiers, and prefetch of an invalid source.

The result line is compact (`passed`, `total`, failures only), because iOS `os_log` truncates messages at about 1 KB.

The failing scenarios carry blurhash and thumbhash placeholders, which must stay visible (`SMOKE_SCREENSHOT=…`). The Android job also runs the core goldens on the emulator (`scripts/test-core-android.sh`).

## 10. Open questions

1. ~~Coil view lifecycle under Fabric recycling.~~ **Resolved by reading the source; the smoke test is consistent with it.** With `target(ImageView)`, Coil:
   - cancels a request that starts before the view is attached and restarts it on attach (Fabric applies props before mounting),
   - disposes on detach and restarts on reattach,
   - stops restarting after our explicit `dispose()`.

   Android Fabric only recycles views for managers that call `setupViewRecycling()`, and TurboImage doesn't. A restart after a completed load re-fires Coil's listener, but the view's handle-identity guard drops it, so `onSuccess` fires once per request. TODO: a long, fast-scrolling list stress test before enabling recycling.
2. ~~Context lifecycle.~~ **Resolved; this RFC was wrong.** Fabric builds each `ThemedReactContext` on top of the root view's context, which is the Activity (`FabricUIManager.startSurface`). Coil's `getLifecycle()` walks the `ContextWrapper` chain, so it finds the Activity. Requests therefore wait for `STARTED` and are disposed on `ON_DESTROY`, without TurboImage doing anything.
3. ~~`cacheOnly` race in the example.~~ **Resolved.** The example is now a deterministic smoke test: scenarios that depend on the cache mount only after the load they depend on has settled.
4. **SPM remote mode** (`RN_SPM_REMOTE_URL`). `Package.swift` supports only RN's local-path mode today.
5. **Host network configuration.** Should adapters accept app-supplied headers, cookies or interceptors? This matters for authenticated images, which 1.x supported through RN's shared `OkHttpClient`.
6. **Nuke 14 adoption.** It raises the iOS floor to 16.0, above RN's 15.1. Adopt it in 2.x only once it is stable and the floor change is acceptable.
